> 论文：Transparent Offloading and Mapping: Enabling Programmer-Transparent Near-Data Processing in GPU Systems (ISCA'16)

## TOM：透明卸载与映射

### 一、摘要

主存带宽是现代GPU系统面临的关键瓶颈，其原因在于有限的片外引脚带宽。3D堆叠存储器架构通过高带宽连接将逻辑层直接连接到DRAM层，为显著缓解这一瓶颈提供了有前景的机会。近期研究表明，一种连接多个此类3D堆叠存储器并将带宽密集型计算卸载至每个逻辑层中GPU的架构，具有可观的潜在性能优势。此类系统中一个尚未解决的关键挑战是，如何在不为程序员增加负担的前提下，实现对多个3D堆叠存储器的计算卸载与数据映射，从而使得任何应用程序都能透明地受益于逻辑层中的近数据处理能力。

我们的论文开发了两种新机制来应对这一关键挑战。第一种是基于编译器的技术，依据简单的成本效益分析自动识别可卸载至逻辑层GPU的代码。第二种是软硬件协同机制，它预测被卸载代码将访问哪些内存页，并将这些页放置在最接近被卸载代码的内存堆叠中，以最小化片外带宽消耗。我们将这两种对程序员透明的机制合称为TOM：透明卸载与映射。

我们在多种现代内存密集型GPU工作负载上进行的大量评估表明，无需任何程序修改，与无法将计算卸载至3D堆叠存储器的基线GPU系统相比，TOM显著提升了性能（平均提升30%，最高提升76%）。

> 这篇论文讨论的不是“在内存旁边放一个计算单元”本身，而是一个更容易被忽略、却决定近数据处理能否真正被使用的问题：当 GPU 系统里有多个带逻辑层的 3D 堆叠内存时，程序员怎样在完全不改代码的情况下，让合适的指令自动跑到离数据最近的地方，并且让数据真的放在那个地方。作者把这套机制命名为 TOM，即 Transparent Offloading and Mapping。
>
> TOM 包含两个主要想法。第一，编译器分析 CUDA 编译产生的 PTX 指令，估算一个指令块如果搬到内存堆叠的逻辑层执行，能省下多少主 GPU 的片外带宽，从而自动找出值得卸载的候选块。第二，系统在程序开始运行时观察少量候选块的内存访问，用这些访问的规律推断最合适的物理地址映射，再把候选块会访问的数据页放到与其执行单元相同的内存堆叠中。由于不同候选块之间的访问强度和片外链路压力会随运行时状态变化，硬件还会动态限制卸载的激进程度，避免逻辑层 SM 被请求压垮，或者把本来不拥塞的链路变成新的瓶颈。
>
> 论文在一个带四个 3D 堆叠内存的 GPU 模型上进行了评估。与不能执行近数据处理的基线 GPU 相比，完整 TOM 平均提升性能 30%，最高提升 76%；片外内存流量平均减少 38%，最高减少 99%；系统能耗平均下降 11%，最高下降 37%。这些数字的意义在于，TOM 的收益并不依赖程序员预先标记数据或重写内核，而是来自编译器、GPU 运行时和硬件控制器之间的一套协作。
>

### 二、现有问题

**1. GPU 的计算能力增长得比片外带宽快**

现代 GPU 常常拥有数十个甚至上百个 SM，但 GPU 与显存之间的引脚、封装和链路带宽增长没有这么快。对于内存密集型应用，SM 并不是没有算力，而是在等待数据。把 DRAM 做成 3D 堆叠并在逻辑层加入计算单元，可以让数据在更靠近内存的位置被消费，减少穿过 GPU 与内存之间片外链路的数据包，因此成为缓解带宽墙的一条自然路径。

**2. 不是所有指令都适合搬到内存旁边**

近数据处理单元通常比主 GPU 小得多，适合处理大量加载和存储、但算术强度不高的指令。如果把包含复杂控制流或大量算术操作的代码也一股脑搬过去，内存堆叠里的 SM 很快就会成为新的计算瓶颈。反过来，如果完全交给程序员判断哪些代码该卸载，就要求程序员了解硬件拓扑、链路方向、寄存器活跃范围和不同阶段的带宽压力；同一个内核换一组输入后，最佳选择还可能变化。论文认为，候选识别应该成为编译器的静态分析问题，而不是 CUDA 程序员的额外负担。

**3. 多个内存堆叠带来了数据放置冲突**

主 GPU 通常把连续 cache line 交错放到不同内存堆叠和 vault，以获得负载均衡和更高的内存级并行度。对于主 GPU，这种映射很合理；但对近数据处理单元来说，最重要的是一段候选代码访问的数据尽量集中在它所在的那个堆叠。如果仍沿用主 GPU 的映射，卸载后的代码可能需要通过堆叠之间的链路读取远端数据，原本想省下的 GPU-内存流量就会变成内存-内存流量。更麻烦的是，不同线程和不同指令块访问的数据范围各不相同，静态地为整个应用选择一种映射很难同时满足两边的需求。

**4. 运行时状态会改变卸载的收益**

编译器可以判断某段代码的静态带宽收支，却无法知道某一时刻逻辑层 SM 上已经排了多少 warp，也不知道 GPU 到内存的 TX、RX 链路是否正在拥塞。若卸载请求超过逻辑层 SM 可同时容纳的 warp 数量，主 GPU 可能停下来等待一个尚未被调度的任务；若候选块只节省 RX 流量，却增加了已经拥塞的 TX 流量，系统同样会变慢。因此，静态候选并不等于必须执行，最终决策需要留给运行时硬件。

### 三、解决方法

主要贡献：

- 我们提出了一种新的基于编译器的机制，用于选择要卸载到近数据计算单元的指令，而无需任何程序员干预。我们的机制通过静态估计不同代码块潜在的内存带宽节省，来识别最适合卸载的候选代码块。我们提出了一种新的运行时机制，根据系统条件决定所选指令是否应该被卸载。
- 我们提出了一种新的对程序员透明的数据映射机制，通过利用被卸载代码块中内存访问模式的可预测性，将卸载代码与数据共同放置在同一内存堆栈中。我们的机制保留所有其他数据的内存映射，以最大化在主GPU上执行的代码的内存带宽。
- 我们对两种机制的组合进行了全面评估，统称为TOM（透明卸载与映射），使用了10个内存密集型的通用GPU应用程序，并涵盖了多种系统配置。我们证明，与无法将计算卸载到3D堆叠内存的基线GPU系统相比，TOM平均将系统性能提升了30%（最高达76%），将片外内存流量减少了38%（最高达99%），并将能耗降低了11%（最高达37%）。

TOM 的整体思路可以概括为一句话：编译器先从“值得尝试”的代码里筛出候选，运行时再根据真实系统状态决定是否执行，数据映射则利用候选块的访问规律把代码和数据放到一起。三部分缺一不可。只有候选识别而没有映射，卸载后的访问仍可能走远端链路；只有映射而没有节流，逻辑层 SM 可能过载；只有硬件而没有编译器信息，硬件就必须在运行时承担复杂的依赖分析。

在编译阶段，TOM 把 PTX 中可能形成的指令块视为候选。它计算候选块进入和离开时需要搬运的 live-in、live-out 寄存器，并估算块内 load/store 被搬到逻辑层后能省下的内存流量。如果节省量超过上下文搬运成本，就给候选块打上标记，同时记录它更可能节省 TX 带宽、RX 带宽，还是两者都节省。循环会根据迭代次数区别处理：静态可知的迭代次数直接纳入估算，运行前才能知道的迭代次数成为带条件的候选，执行过程中才逐步决定的循环则采用保守估计。

数据映射采用一个短暂的学习阶段。系统先不急着把数据复制到 GPU 显存，而是让初始候选实例通过 CPU 内存运行，硬件记录它们在不同连续地址位映射下会触及多少个内存堆叠。观察到足够少的样本后，运行时选择使候选访问最集中于单一堆叠的位段，并要求驱动把候选访问过的数据页按这个映射复制到 GPU；其余数据仍采用有利于主 GPU 带宽均衡的默认映射。论文发现只观察约 0.1% 的候选实例，就能得到接近全量观察的结果，所以学习阶段不会变成长期的额外执行模式。

最后，硬件的卸载控制器在每个候选入口处检查条件、链路繁忙状态和目标堆叠的待处理请求数。只有这些条件都允许时，才把 warp 的寄存器上下文、起止 PC 和 active mask 打包后发往逻辑层 SM。任务完成后，逻辑层返回 live-out 寄存器和需要失效的 cache line，主 GPU 再从候选块结束位置继续执行。对程序员而言，这些动作发生在普通 CUDA 内核内部，应用不需要调用新的卸载 API。

### 四、技术细节

#### 1. 系统组织：主 GPU 与内存堆叠中的 SM 协作

![TOM 系统组织]({{ '/assets/images/tom/image-20260907121823104.png' | relative_url }})

论文抽象的系统由一个主 GPU 和多个 3D 堆叠内存组成。每个内存堆叠的逻辑层放置一个 SM，逻辑层通过 TSV 直接连接 DRAM 层；主 GPU 与每个堆叠之间有独立的双向片外链路，堆叠之间还通过较窄的 cross-stack 链路互连。主 GPU 负责运行完整 CUDA 程序，也负责发起卸载；内存堆叠中的 SM 不运行独立的操作系统或完整应用，只执行主 GPU 转交的候选指令块。

评估配置包含四个内存堆叠，每个堆叠有 16 个 vault、每个 vault 有 16 个 bank 和 64 条 TSV。GPU 到每个堆叠的链路带宽为 80 GB/s，总带宽 320 GB/s；堆叠内部带宽按每堆叠 160 GB/s 建模，堆叠之间的链路为 GPU-堆叠链路的 0.5 倍。基线 GPU 使用 68 个 SM，TOM 系统主 GPU 使用 64 个 SM，并把每个堆叠的一个逻辑层 SM 算入总计算资源。这样比较的是“把部分工作移到内存旁边”与“把所有工作留在更多主 GPU SM 上”的差异，而不是简单增加总 SM 数量。

#### 2. 编译器如何判断一个块值得卸载

在识别适合卸载的候选指令块时，目标是通过减少主GPU的内存带宽消耗来提高性能。这种识别的关键在于判断：卸载某个指令块在卸载执行期间节省的内存带宽，是否大于为启动并完成该卸载而产生的额外数据传输开销。内存带宽的节省来自于在内存堆栈中执行被卸载的加载/存储操作。卸载的开销则源于将指令块在内存中执行所需的上下文传输到内存，以及将执行结果返回主GPU。

![候选块卸载的带宽成本收益]({{ '/assets/images/tom/图片1.png' | relative_url }})

候选识别的核心是带宽成本收益分析。对于单线程、独立执行的 load/store，作者先给出一个假设的直观模型。设候选块需要传入和传出的寄存器数分别为 `REG_TX` 和 `REG_RX`，块内 load、store 数量分别为 `N_LD` 和 `N_ST`，则 TX、RX 方向的带宽变化可写成：

```text
BW_TX = REG_TX - (N_LD + 2 * N_ST)
BW_RX = REG_RX - (N_LD + 1/4 * N_ST)
```

如上图所示，原本这一计算块是在GPU的计算单元上完成，需要对GPU的显存进行访问，这一计算块所需发送和接收的数据就是公式中所写的`N_LD`，`N_ST`。由于这部分对显存的访问，通过把计算块搬运到HBC（本文中假设的3D堆叠内存，带有计算功能）从而节省了计算块对于显存的访问，但额外带来了需要GPU把运算上下文发送给HMC的数据传输。如果额外增加的比节省的要少，则这一次卸载是有意义的。

这里的正负号表示“卸载后相对于留在主 GPU 上执行的变化”。load 需要经 TX 发送地址、经 RX 返回数据；store 需要经 TX 发送地址和数据、经 RX 返回较小的确认消息。论文假设地址、数据和寄存器的大小是确认消息的四倍，所以 store 在两个方向上的权重不同。若 `BW_TX + BW_RX` 为负，说明省下的内存流量超过了传递执行上下文的成本。

真实 GPU 以 warp 为单位执行，load/store 还会经过合并和 cache line 访问，因此论文进一步把模型改写为 warp 粒度：

```text
BW_TX = (REG_TX * S_W)
        - (N_LD * Coal_LD * Miss_LD
           + N_ST * (S_W + Coal_ST))

BW_RX = (REG_RX * S_W)
        - (N_LD * Coal_LD * S_C * Miss_LD
           + 1/4 * N_ST * Coal_ST)
```

`S_W` 是 warp 大小，`S_C` 是 cache line 大小与地址大小的比值，`Coal_LD`、`Coal_ST` 是 load 和 store 的合并比例，`Miss_LD` 是 load 的 cache miss 率。由于编译器不知道运行时真实的合并程度和 miss 率，论文采用保守参数：假设 load/store 都完全合并，`Miss_LD` 取 50%。编译器能够准确得到寄存器依赖，是因为这些信息本来就用于寄存器分配和指令调度；而把合并比例、cache miss 率留给运行时并不现实。

循环是这个模型里很关键的一点。一次循环的卸载上下文成本基本固定，但循环体中的 load/store 会随着迭代次数线性增加，所以一个单次执行看似不划算的块，循环多跑几次后可能变得非常适合卸载。若迭代次数编译期已知，编译器直接把它乘进收益；若在进入循环前才能知道，编译器把循环标成条件候选，并把条件交给硬件；若迭代次数要在循环执行中才逐步产生，编译器先按一次迭代保守判断，只有循环体本身值得卸载时才标记为无条件候选。论文用 LIBOR Monte Carlo 的两个循环说明了这一点：在保守 miss 率下，单次执行并不节省带宽，但循环至少迭代四次后，累计收益就转为正值。

为了保证卸载语义可控，TOM 对候选块施加三个限制。候选块不能访问主 GPU 的片上 shared memory，因为内存堆叠 SM 无法直接读取它；如果 warp 内线程发生分支，所有控制流必须在候选块结束前重新汇合；块内不允许 memory barrier、同步和 atomic 指令，因为论文没有为主 GPU 与逻辑层 SM 之间建立这些同步原语。换句话说，TOM 优先处理无同步、规则的内存密集型片段，而不是试图把任意 CUDA 控制流搬到内存旁边。

#### 3. 数据映射：用固定偏移把访问集中到同一堆叠

我们发现，通过观察少量初始卸载候选实例的内存行为，可以预测最佳的内存映射。图6展示了仅通过观察前0.1%、0.5%和1%的卸载候选实例来做出内存映射选择时，能达到的接近程度。该图显示，仅观察0.1%的卸载候选实例后所选择的映射，其访问单个内存堆栈的概率达到72%，仅比通过Oracle知识获得的结果低3%。这符合直觉，因为大多数GPU程序根据线程和线程块的索引来访问内存，这使得线程间的访问模式高度可预测且一致。我们得出结论：通过观察少量初始卸载候选实例，可以预测出一种简单的内存堆栈物理地址映射，从而显著改善代码/数据在内存位置上的共置性。

![透明数据映射的学习效果]({{ '/assets/images/tom/屏幕截图 2026-09-07 141316.png' | relative_url }})

TOM 的数据映射建立在一个经验观察上：大量候选块的地址访问具有固定偏移。若两个数组使用同一个线程索引访问，那么它们的地址差主要由数组基址决定；若这个差值包含 `2^M` 因子，访问地址的一些低位就会保持一致。系统可以选择连续的地址位来决定内存堆叠索引，使这些固定偏移的访问落入同一个堆叠。

借助我们的机制，GPU内核执行被划分为一个相对较短的初始学习阶段和随后的常规执行。在学习阶段，所有GPU内核在主SM上运行，相应的数据驻留在CPU内存中，同时该机制为卸载候选者所访问的数据学习最佳内存映射。学习阶段结束后，在常规执行开始之前，我们根据学习到的最佳内存映射，将卸载候选者访问的数据从CPU内存复制到GPU内存。我们的机制本质上是在典型GPU执行流程中延迟从CPU到GPU的内存复制，因此不会产生额外的数据重映射开销。在常规执行期间，被卸载的代码在内存堆栈SM上运行，而其访问的数据则使用学习阶段发现的最佳映射进行映射。由于我们仅将最佳映射应用于卸载候选者访问的数据，所有其他数据仍使用GPU通常采用的复杂内存映射方案进行映射，该方案为主GPU执行的代码最大化内存带宽。

映射位不能取 cache line 内的偏移，否则会破坏链路传输效率；也不宜随意取过高位，否则可能影响 DRAM 行缓冲局部性。假设固定偏移至少含有 `2^M` 因子，cache line 大小为 `2^N`，候选位段就在 `[M-1:N]` 范围内搜索。四个堆叠只需要两位地址位来形成堆叠索引，论文会枚举这些连续两位的所有选择，再比较候选实例访问单一堆叠的概率。

在十个 GPU 工作负载中，约 85% 的候选块至少有一部分固定偏移访问，六个工作负载的候选块完全由固定偏移访问构成。使用最佳连续位段后，候选实例只访问一个堆叠的概率从默认映射的 38% 提升到平均 75%，接近两倍。这个结果并不意味着所有数据都要按同一种“局部化”规则放置：TOM 只对候选块会访问的数据采用该映射，其余数据仍按主 GPU 的交错策略放置，避免为了少数卸载块牺牲主 GPU 的带宽。

#### 4. 程序员透明映射机制运行流程

```
主 GPU 执行
    |
    v
发现候选块入口
    |
    v
Offload Controller 检查条件、链路和近存 SM 容量
    |
    +-- 不适合 --> 主 GPU 正常执行候选块
    |
    +-- 适合 --> 发送 live-in、PC、active mask
                       |
                       v
                 近存 SM 执行候选块
                       |
                       v
                 返回 live-out 和失效信息
                       |
                       v
                 主 GPU 更新状态并继续执行
```

我们提出的程序员透明数据映射是一种软硬件协同机制，基于少量初始卸载候选实例的访问模式，选择并应用最佳的内存映射以实现计算/数据共置。在硬件方面，我们在GPU中添加了一个内存映射分析器。在软件方面，我们修改了运行在CPU上的GPU主机端驱动程序和运行在GPU上的GPU运行时。现有应用程序无需任何程序修改即可受益于我们的程序员透明数据映射。

这一机制包含以下五个步骤：

第一步发生在 kernel 启动前。驱动照常为应用分配 GPU 虚拟地址，但暂时不把对应内容复制到 GPU 显存，而是先让这些虚拟地址指向 CPU 内存，并把每个分配记录在 memory allocation table 中。这样做把原本发生在 kernel 启动前的复制延后，为学习阶段留下观察窗口。

第二步，应用照常发起 kernel。运行时根据分配表和编译器生成的 offloading metadata table 配置 memory map analyzer。学习阶段的初始线程仍在主 GPU 上执行，访问通过 GPU-CPU 链路到达 CPU 内存，论文在实验中计入了这部分 PCIe 延迟。

第三步，memory map analyzer 观察线程的地址访问。对于每个候选实例，它会计算在不同两位连续地址映射下需要访问多少个堆叠；同时，它在分配表中标记哪些内存范围确实被候选块访问过。

第四步，当观察到预设比例的候选实例（论文默认约 0.1%）后，分析器向 GPU runtime 发起中断。runtime 暂停 GPU 上的执行，根据访问统计选择使候选块访问最集中于目标堆叠的映射。

第五步，runtime 要求驱动完成真正的数据复制。被候选块访问过的页按新映射放入 GPU 显存，其他页沿用主 GPU 友好的默认映射。复制和页表设置完成后，常规执行恢复，后续候选块便可以在数据所在的逻辑层 SM 上运行。由于论文把重映射嵌入了原有的 CPU 到 GPU 数据复制过程，因此不需要在学习结束后再额外搬运一遍数据。

#### 5. 动态卸载节流：让静态候选服从实时状态

编译器只负责告诉硬件“这个块有潜力”，最终是否卸载由 Offload Controller 决定。它会依次检查三个条件。对于条件候选，先从 Operand Collector 读取相关寄存器，判断循环次数等条件是否满足；然后查看 Channel Busy Monitor 报告的 TX、RX 链路利用率，如果该块会增加已经拥塞的方向流量，就留在主 GPU 执行；最后根据候选块第一条内存指令确定目标堆叠，检查该堆叠逻辑层 SM 的待处理请求是否已经达到可并发 warp 上限。

如果决定卸载，主 GPU 把 live-in 寄存器、候选块起止 PC 和 active mask 打包成请求发往目标堆叠。论文在模拟中假设发送一个卸载任务需要 10 个周期，而候选块中的一次内存访问至少需要约 200 个周期，因此只要块内确实包含多次内存访问，启动成本就相对较小。逻辑层 SM 执行结束后返回 live-out 寄存器以及被写入的 cache line 地址，主 GPU 让相关 cache line 失效，并从候选块之后的指令继续运行。

这个控制机制直接解释了论文中“总是卸载”反而变慢的现象。若所有候选都发送到逻辑层，内存堆叠的 SM 会因为 warp 容量有限而排队，主 GPU 也会在等待请求完成时停顿。另一种情况是候选块节省 RX 流量却增加 TX 流量，此时盲目卸载会把压力推向更紧张的方向。TOM 用候选块的 2 位带宽标签和实时链路利用率把这两类情况过滤掉。

#### 6. 硬件新增模块与元数据接口

![TOM 的硬件模块与元数据接口]({{ '/assets/images/tom/image-20260907142106036.png' | relative_url }})

为了把上述决策接入普通 GPU 流水线，论文新增三个主要硬件模块。Offload Controller 负责读取候选元数据、做最终决策、封装请求和接收确认；Channel Busy Monitor 记录片外 TX/RX 链路的利用率，在超过阈值时标记为 busy；Memory Map Analyzer 只在学习阶段开启，统计不同地址位映射对应的堆叠访问数量。

- **卸载控制器**与主GPU流水线协同工作，提供三项功能。首先，它根据运行时信息确定是否应卸载某个候选块。该运行时决策涉及对条件性卸载候选的处理以及动态卸载激进程度控制。其次，它将卸载信息打包并发送至内存堆栈SM。第三，当它收到来自内存堆栈SM的相应确认数据包时，恢复被卸载的线程束。
- **通道忙闲监视器**跟踪片外TX/RX通道的利用率。当某通道的利用率达到预定义阈值时，它会向卸载控制器报告该通道为忙。
- **内存映射分析器**由GPU运行时设置，用于针对所有不同的潜在堆叠映射，提供每个卸载候选实例所访问的内存堆叠数量。该单元仅在程序员透明数据映射的学习阶段启用。

编译器与硬件之间的接口：编译器通过两种方式向硬件提供有关卸载候选的信息。首先，我们在ISA（指令集架构）中引入一条新指令，编译器用该指令向硬件指示卸载候选块的开始。其次，编译器在程序中向硬件提供一个卸载元数据表。该表中的每个条目与一个卸载候选相关联，并提供起始/结束PC地址、live-in/live-out寄存器、用于指示TX/RX通道节省的2位标签，以及条件性卸载候选的条件。该表由编译器分配，并放置在片上共享内存中。

进行NDP卸载的详细过程如下，主要包含卸载候选块检测、动态卸载决策、发送卸载请求、接收卸载确认。

卸载候选块检测：在流水线中，每条指令被解码并放入指令缓冲区。当指令缓冲区检测到某条指令是卸载候选块的开头时，它会将该线程束标记为未就绪，并向卸载控制器请求卸载决策。卸载控制器从共享内存获取其卸载元数据，并利用该元数据做出卸载决策。

动态卸载决策包含三个步骤：

（1）对于条件卸载候选，卸载控制器检查卸载条件是否为真。它通过从操作数收集器获取相应的寄存器值，并根据相应条件执行值比较来完成检查。

（2）如果发送/接收（TX/RX）通道之一被通道忙监视器标记为忙，且该块的2位标签指示其将向该忙碌通道引入更多内存流量，则卸载控制器不会卸载该块。

（3）卸载控制器根据该块第一条指令将访问的内存堆栈确定卸载目标。

然后，它检查发往该内存堆栈的待处理卸载请求数量是否已达到该内存堆栈SM的线程束限制，若已达到，则跳过卸载。注意，在等待卸载决策期间，流水线可以调度并执行其他线程束。

发送卸载请求：指令缓冲检测到候选入口后，会先把 warp 标记为不可运行并查询控制器；若不卸载，流水线照常执行；若卸载，Issue 单元把后续指令交给控制器封装。

接收卸载确认：当卸载的块在内存栈上完成执行时，内存栈SM会向主GPU发送一个卸载确认数据包，其中包含活跃输出寄存器和需要失效的缓存行。卸载控制器请求缓存失效和寄存器更新，然后在GPU上从该块末尾的下一条指令处重新启动相应的线程束。

#### 7. 地址转换与 cache 一致性

内存堆叠中的 SM 仍然看到 GPU 虚拟地址，因此论文假设每个逻辑层 SM 配有 TLB 和 MMU。估算表明，地址转换硬件只需要约 1-2K 个触发器和少量逻辑，占内存堆叠 SM 面积不到 2%。页表可能位于其他堆叠，这时通过已有的 cross-stack 链路访问；由于 TOM 只在数据复制和页表更新完成后才开始卸载，也不需要在运行中频繁做 TLB shootdown。

cache 一致性则不能直接照搬多核 CPU 的全局协议，因为那会在 GPU 与多个堆叠之间引入大量额外流量。TOM 利用 CUDA 的 CTA 语义，把同一个 CTA 中的卸载块视为请求 SM 的延伸，并采用三步处理：主 GPU 在发起卸载前把自己的写回流量推到内存；内存堆叠 SM 生成新 warp 前先使自己的私有 cache 失效；卸载块结束时，逻辑层记录其写过的 cache line，并把地址返回主 GPU，由请求 SM 让这些行失效。这样主 GPU 下一次读取时会从内存得到最新值。论文测得这套一致性处理平均只带来 1.2% 的性能开销，但它要求候选块内部不含显式同步指令，并依赖不同 CTA 之间本来就没有隐式顺序保证这一事实。

### 五、实验内容

#### 1. 模拟平台与对比方法

![实验模拟平台]({{ '/assets/images/tom/image-20260909141645262.png' | relative_url }})

作者修改 GPGPU-Sim 3.2.0，加入内存堆叠逻辑层 SM、GPU-堆叠链路和堆叠间链路，并用 BookSim 模拟互连网络。功耗部分使用 GPUWattch 估算 GPU SM 和片上互连，再用 Rambus 模型估算 TSV 与 3D DRAM 的能耗。实验把 live-in/live-out 寄存器传输、学习阶段的 PCIe 延迟和 cache 一致性流量都计入模型。

![评估工作负载]({{ '/assets/images/tom/image-20260909141908960.png' | relative_url }})

工作负载来自 Rodinia、GPGPU-Sim 和 CUDA SDK，筛选标准是内存带宽利用率超过 50%。十个应用包括 Back Propagation、BFS、K-means、CFD、Heartwall、LIBOR Monte Carlo、Ray Tracing、Fast Walsh Transform、Scalar Product 和 Parallel Reduction。主要指标是相对基线的 IPC，同时报告所有片外链路上的总流量，并把流量拆成 GPU-内存 RX、GPU-内存 TX 和 memory-to-memory 三类。

实验分别组合两种卸载策略和两种数据映射：`NDP-Uncontrolled`（`no-ctrl`）总是卸载编译器标记的候选，`NDP-Controlled`（`ctrl`）启用动态节流；`bmap` 是基线 GPU 映射，`tmap` 是 TOM 的透明映射。除特别说明外，结果都相对于“不带 NDP、使用基线映射”的 GPU。

#### 2. 性能结果：节流和映射必须同时存在

![不同卸载与映射策略的性能]({{ '/assets/images/tom/image-20260909141942160.png' | relative_url }})

完整 TOM，即 `ctrl + tmap`，平均性能提升 30%，最高提升 76%，而且十个工作负载都获得了不同程度的提升。基线和 TOM 主 GPU 的 SM 数量相同，因此这说明把部分内存密集型工作移到堆叠逻辑层，比单纯在主 GPU 上保留更多 SM 更有效。

透明数据映射在 NDP 之上平均再带来约 10% 的收益。K-means 的提升从只有 3% 变成 39%，Parallel Reduction 从 51% 变成 76%，说明数据是否和代码落在同一堆叠上会显著影响卸载效果。BFS 是例外，它的访问非常不规则，早期 0.1% 样本选出的映射不一定适合后续所有实例，因此提升从 29% 降到 21%；如果知道全局最优映射，论文估计 BFS 可以达到 64% 的提升。

动态节流是 NDP 能否稳定提速的关键。关闭节流时，即使使用 tmap，系统平均也会慢 3%；使用 bmap 时平均慢 7%。LIBOR Monte Carlo 的差异最明显：不节流时性能下降 64%，打开节流后则提升 52%。节流把实际卸载的指令比例从 46.4% 降到 15.7%，但留下来的候选更符合逻辑层 SM 和片外链路的承载能力。

#### 3. 内存流量和能耗

![片外内存流量与能耗结果]({{ '/assets/images/tom/image-20260909142009913.png' | relative_url }})

如果把所有候选都卸载并使用 tmap，片外总流量平均下降 38%，最高下降 99%；启用节流后，由于部分内存密集型候选被留在主 GPU，流量下降变为平均 13%、最高 37%。这是一组很有代表性的性能-流量权衡：节流牺牲了一部分流量削减，却换来了更稳定的执行时间。

数据映射对 memory-to-memory 流量的作用尤其直接。在全部候选卸载的情况下，基线映射下 memory-to-memory 流量约占基线总流量的 55%，换成 tmap 后降到 22%，减少约 2.5 倍。原因不是内存堆叠之间的链路更快了，而是更多访问在本地堆叠完成，不再需要为远端数据付出一次额外搬运。

完整 TOM 平均减少系统能耗 11%，最高减少 37%。能耗中主 GPU/逻辑层 SM 的占比从基线的 77% 降到 68%，片外链路占比从 7% 降到 5%。有意思的是，只减少流量并不保证省电：如果没有数据映射或没有动态节流，系统平均反而增加 8% 能耗，因为执行时间拉长后，SM 的静态泄漏能量超过了少传输一些数据带来的收益。

#### 4. 设计空间探索

论文还考察了逻辑层 SM 资源和链路带宽变化后的趋势。把内存堆叠 SM 的 warp 容量增加到 4 倍，相比 1 倍容量可额外减少约 20% 的内存流量，同时保持相近的性能收益；相对基线，平均性能提升约 29%，接近不加节流时的流量削减效果。这个结果说明，节流的主要原因不是候选无效，而是逻辑层的并发容量有限。不过 Parallel Reduction 在 warp 容量增大后明显变慢，因为它的候选块中 ALU 指令比例较高，更多并发反而把计算流水线变成瓶颈。

把堆叠内部带宽从默认的外部链路 2 倍降到 1 倍，平均性能仍在 2 倍内部带宽结果的 2% 以内，平均比基线快 28%。这说明 TOM 的收益并不完全依赖一个极高的 TSV 内部带宽，主 GPU 先被某一条 TX/RX 链路卡住时，逻辑层 SM 即使只拥有与外部相当的带宽，也能利用原本闲置的路径。堆叠间链路带宽取 GPU-堆叠链路的 0.125、0.25 和 1 倍时，平均性能收益分别为 17%、29% 和 31%，表明方案在一段较宽的链路设计空间内都有效。

最后，作者用 CACTI 6.5 估算 memory map analyzer、memory allocation table 和 offloading metadata table 的面积，得到总开销约 0.11 mm²，仅占建模 GPU 面积的 0.018%。这个数字表明，TOM 的主要难点不是增加了一个很大的计算阵列，而是如何把分析结果、运行时状态和内存映射正确接入 GPU 的执行路径。

### 六、存在的不足

**1. 结果依赖体系结构模拟，缺少真实芯片验证**

论文的贡献是系统机制和端到端建模，而不是一颗已经流片的产品。内存堆叠逻辑层 SM、cross-stack 链路、片外链路功耗以及 DRAM 时序都来自模拟器和功耗模型。特别是 2 倍内部带宽、每个堆叠一个 48-warp SM 等参数，会影响可达到的收益，真实 3D 堆叠实现还要面对热、面积、供电和封装约束。

**2. 透明映射的学习阶段仍有额外成本和适用边界**

学习阶段把数据暂时留在 CPU 内存，初始访问要经过 PCIe；虽然论文把这段延迟计入实验，而且只观察 0.1% 候选实例，但短 kernel、小数据集或频繁重复启动的应用未必能摊平这笔成本。更重要的是，tmap 假设早期访问可以代表后续访问。BFS 的结果已经显示，强不规则、随输入变化明显的访问模式可能让早期选出的映射失准。

**3. 候选块的静态分析有明确限制**

编译器模型使用固定的 50% load miss 率和完全合并的访问作为保守估计，真实 cache 行为、分支行为和不同输入规模可能使候选质量偏离估计。候选块不能含 shared memory、atomic、同步和未在块内汇合的分支，这意味着一部分常见 CUDA 优化代码无法直接受益。论文的分析工具针对 PTX 实现，迁移到真实 GPU 还需要适配具体的 SASS 或其他指令集格式。

**4. 性能和流量之间存在不可消除的取舍**

关闭节流可以平均省掉 38% 流量，却平均损失 3% 性能；打开节流后性能提升 30%，流量只减少 13%。增加逻辑层 SM 的 warp 容量能缓解这个问题，但需要更多寄存器、warp 状态和调度器，并且会让计算密集的候选块在逻辑层形成新瓶颈。TOM 目前的节流主要看待处理 warp 数和 TX/RX 链路利用率，对候选块内部 ALU 比例的判断还不够细，论文也把更精细的节流策略留作后续工作。

**5. 一致性方案建立在 GPU 编程模型的前提上**

TOM 没有实现主 GPU 与所有堆叠 SM 之间的通用 cache coherence，而是利用同一 CTA 的执行关系、显式同步要求和候选块禁止同步等约束来保证正确性。这种方式开销小，但适用范围也更窄。若未来 GPU 支持更复杂的共享内存语义、异步任务或跨 CTA 协作，就需要重新审视 cache 失效时机和可见性保证。

**6. 多堆叠扩展会放大映射和元数据管理难度**

论文评估的是四个内存堆叠，映射搜索只需要枚举连续两位地址位。堆叠数量增加后，堆叠索引需要更多位，候选块之间的局部性冲突、远端访问比例和 memory map analyzer 的状态量都会增加。与此同时，页表可能位于远端堆叠，cross-stack 链路也可能成为新的瓶颈。TOM 证明了透明映射在中等规模系统中的可行性，但并没有给出大规模堆叠网络下的全局映射策略。

总体来看，TOM 最重要的价值不是宣称所有 GPU 代码都应该搬到内存旁边，而是把近数据处理从“需要程序员手工管理的特殊模式”变成了一个可以由编译器、运行时和硬件共同完成的普通执行优化。它同时揭示了一个现实：NDP 的难点从来不只是把计算单元放到 DRAM 旁边，还包括候选选择、数据落点、链路拥塞、缓存一致性和任务容量这些系统层问题。TOM 给出的答案并不完美，却为后来更复杂的 GPU 近数据处理和透明内存优化提供了一个很清晰的起点。
