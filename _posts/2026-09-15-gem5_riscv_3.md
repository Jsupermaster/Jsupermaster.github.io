# Gem5全系统仿真运行实录（基于RISC-V）

# 第三章：Gem5的运行机制与原理

前两章中，我们借助Gem5的自带CPU完成了SoC搭建，运行了裸机Hello,world，并最终启动了Linux系统。这一过程中，我们主要使用Gem5的TimingSimple CPU完成了片上系统和板级硬件系统搭建，为其连接了内存、硬盘，并连接了UART串口外设，学习了如何通过Python脚本对Gem5进行配置。

然而，进一步的研究过程中，我们需要对Gem5的设计思路、运行原理有更加深入的理解，从而在后期为自己的CPU设计模拟器，并通过各类组件实现外联GPU、NPU等其他模拟器或更高级的体系结构模拟。为此，这一章我们详细讲解Gem5的运行机制与原理，并搭建自己的CPU外围框架，为后续进一步完善CPU设计做铺垫。

本章的内容主要分为五个部分。首先介绍Gem5的仿真框架，从配置脚本、SimObject、事件驱动机制、端口与内存请求等方面说明一个Gem5系统是如何被创建并运行起来的；然后以一段简单程序为例，详细追踪TimingSimpleCPU从取指请求、Cache响应到指令执行的完整过程；随后介绍Gem5提供的微架构模型，分析AtomicSimpleCPU、TimingSimpleCPU、MinorCPU和O3CPU等模型的执行方式，以及它们在整个运行系统中的作用；接着介绍Gem5对ISA和具体架构的支持，重点分析RISC-V指令集相关的寄存器、指令解码、PC状态、内存管理、异常中断和特权级等内容，并说明ISA如何与CPU微架构进行配合；最后讨论如何将自定义CPU接入Gem5，包括外围框架、编译注册、系统配置和裸机程序启动过程，为后续逐步实现支持RV32I的单周期CPU做好准备。

## 3.1 Gem5仿真框架

**Gem5并不是一个单独的CPU程序**

从使用方式上看，我们通常通过一个Python脚本启动Gem5，创建一个System对象，连接CPU、内存、总线和外设，然后调用`m5.simulate()`开始仿真。这种使用方式容易让人产生一种错觉，似乎Gem5只是按照配置文件中的顺序依次调用这些对象。但实际上，Python脚本只负责创建和连接仿真对象，真正的执行过程由C++实现的事件驱动框架完成。

Gem5中的CPU、Cache、总线、内存控制器、磁盘、UART和中断控制器都属于相互独立的仿真对象。它们通过端口建立连接，通过Request和Packet传递访问请求，并通过事件队列协调不同组件之间的执行时间。因此，Gem5的基本结构可以概括为如上图所示：

```text
Python配置脚本
        |
        v
创建和连接SimObject
        |
        v
初始化系统状态和Workload
        |
        v
事件队列驱动CPU、内存和设备
        |
        v
完成指令执行和外设交互
```

这种结构使Gem5具有较强的可扩展性。研究者可以只替换CPU模型，而保留原有的内存系统和设备模型；也可以保留CPU和内存系统，只替换某个Cache、互连结构或者设备模型。

**Python配置脚本与仿真启动**

Gem5通常不会在C++代码中直接创建完整系统，而是把系统组成交给Python脚本配置。例如，一个最基本的系统配置通常需要完成以下工作：

```python
system = System()
system.cpu = TimingSimpleCPU()
system.membus = SystemXBar()
system.mem_ctrl = MemCtrl()
system.workload = RiscvBareMetal()
```

这些语句并不会立即执行CPU，也不会立刻把内存控制器创建成一个正在工作的硬件模块。它们首先在Python侧构造SimObject对象，设置参数，并建立对象之间的层次关系和端口连接。

`Root`对象表示整个仿真的根节点。配置脚本完成后，Gem5通过下面的代码正式进入初始化过程：

```python
root = Root(full_system=True, system=system)
m5.instantiate()
m5.simulate()
```

`m5.instantiate()`是Python配置和C++仿真对象之间的连接点。在这个阶段，Gem5会根据Python对象生成的参数，创建对应的C++对象，建立父子关系，连接端口，并完成各个组件的初始化。对于RISC-V裸机系统来说，Workload也会在这一阶段准备程序镜像和线程上下文。

`m5.simulate()`启动真正的仿真过程。它并不是简单地调用CPU的某个函数循环执行，而是进入Gem5的事件队列，从当前仿真时间开始，不断取出最早发生的事件并执行。CPU的取指事件、内存响应事件、UART事件和定时器事件，都通过这种方式被调度。

**SimObject与Python、C++的对应关系**

Gem5中的SimObject通常由三部分共同组成。第一部分是Python配置类，负责声明类型、参数和对象之间的配置关系；第二部分是C++头文件，负责声明真正的C++类；第三部分是C++源文件，负责实现对象的构造函数和具体行为。

下面用一个抽象的`ExampleCPU`表示Python侧的定义：

```python
class ExampleCPU(BaseAtomicSimpleCPU, RiscvCPU):
    type = "ExampleCPU"
    cxx_class = "gem5::ExampleCPU"
    cxx_header = "path/to/ExampleCPU.hh"

    mmu = RiscvMMU()
```

其中，`type`是Gem5内部使用的SimObject类型名称，`cxx_class`指定对应的C++类，`cxx_header`指定C++类的头文件。`BaseAtomicSimpleCPU`提供了AtomicSimpleCPU所需的Python参数和CPU模型定义，`RiscvCPU`则提供RISC-V相关的Decoder、MMU、ISA和中断控制器类型。

这段代码中的多重继承并不是让Python类独立实现一套CPU，而是把通用CPU模型和RISC-V架构支持组合到一起。真正的C++实现位于组件声明的头文件和源文件中，具体路径由构建配置决定。

Gem5的参数系统会根据Python类中的参数定义生成对应的C++参数结构。例如，`BaseAtomicSimpleCPU`中的`width`、`simulate_data_stalls`等参数，最终会进入`BaseAtomicSimpleCPUParams`。在C++类中通过`PARAMS(ExampleCPU)`宏，就可以获得`ExampleCPUParams`类型，并在构造函数中传递给父类。

**SCons构建过程**

Gem5并不是自动扫描所有目录中的C++文件。自定义组件必须通过`SConscript`加入构建系统。下面用`ExampleCPU`表示一个需要加入构建系统的组件：

```python
Import("*")

if env["CONF"]["BUILD_ISA"]:
    SimObject("ExampleCPU.py", sim_objects=["ExampleCPU"])
    Source("ExampleCPU.cc")
```

`SimObject("ExampleCPU.py")`告诉Gem5构建系统，这个Python文件中定义了一个需要生成绑定信息的SimObject；`Source("ExampleCPU.cc")`则把C++实现文件加入编译过程。只有完成这一步，Gem5才会在构建时生成`params/ExampleCPU.hh`等参数文件，并把`ExampleCPU.cc`编译进最终的Gem5二进制程序。

在使用外部目录扩展Gem5时，还需要通过`EXTRAS`将扩展目录交给构建系统。例如：

```bash
scons EXTRAS=$PWD/path/to/extensions build/RISCV/gem5.opt -j2
```

构建过程大致可以表示为：

```text
读取SConscript
        |
注册Python SimObject
        |
生成params/ExampleCPU.hh
        |
编译ExampleCPU.cc
        |
链接到gem5.opt
```

这里需要区分“Python对象被注册”和“CPU执行逻辑被实现”这两个概念。完成SimObject注册只说明Gem5能够识别并创建这个CPU对象，并不意味着我们已经实现了新的指令执行过程。

**事件驱动模型**

Gem5采用离散事件仿真。仿真时间不是现实世界中的时间，而是由`Tick`表示的逻辑时间。一个组件如果希望在未来某个时刻继续工作，就需要向事件队列中安排一个事件。

例如，CPU在一个时钟周期发起取指请求，内存系统在若干个Tick之后返回响应。对于Timing访问，这个响应会被安排成一个未来事件；当事件到达时，CPU的端口回调函数被调用，CPU再恢复执行。UART发送字符、定时器到期和外部中断产生，也采用类似的方式。

因此，Gem5中的“运行”更接近下面的过程：

```text
当前时间 = 0
    |
取出时间最早的事件
    |
执行事件对应的处理函数
    |
产生新的事件
    |
推进到下一个事件的时间
    |
循环执行
```

CPU模型通常会有一个或多个事件作为自己的驱动。例如，AtomicSimpleCPU内部使用`tickEvent`，TimingSimpleCPU内部使用`fetchEvent`。这些事件不是普通的C++函数调用，而是注册在Gem5事件队列中的可调度对象。

在AtomicSimpleCPU中，构造函数会将`tickEvent`绑定到CPU的`tick()`函数。CPU被激活后，Gem5调度这个事件，`tick()`执行一组指令，然后再安排下一次事件。TimingSimpleCPU则会在取指、等待Cache响应和继续执行之间切换不同的状态。

**Port、Request和Packet**

Gem5组件之间的通信主要通过Port完成。CPU通常具有指令端口和数据端口，Cache或总线则提供与之对应的连接端口。在典型的系统配置中，CPU端口连接到系统总线：

```python
system.cpu.icache_port = system.membus.cpu_side_ports
system.cpu.dcache_port = system.membus.cpu_side_ports
```

这里的`icache_port`用于指令访问，`dcache_port`用于数据访问。如果CPU和总线之间没有显式创建Cache，CPU就会直接连接到总线；在更复杂的系统中，通常会变成：

```text
CPU
 |
L1 I-Cache / L1 D-Cache
 |
L2 Cache
 |
SystemXBar
 |
Memory Controller
```

一次内存访问通常至少包含三个层次的对象。`Request`描述一次访问的基本信息，例如地址、大小、访问类型、上下文和请求者；`Packet`在Request的基础上描述一次具体的网络传输，并携带数据或响应状态；`Port`负责将Packet从一个组件发送到另一个组件。

以取指为例，CPU首先根据PC创建指令请求，并通过指令端口发送。总线根据地址寻找目标端口，内存控制器接收请求后访问实际存储介质，再将响应Packet沿原路径返回。对于数据访问，流程类似，只是请求类型可能是读、写、原子操作或内存管理操作。

对于自定义CPU来说，端口是必须认真处理的接口。CPU至少需要能够发起指令访问和数据访问，并在访问完成后将数据交给执行逻辑。采用Atomic访问时，访问可以在一个函数调用中完成；采用Timing访问时，则必须保存未完成请求的状态，并等待端口回调。

**Atomic、Timing和Functional访问**

Gem5中的三种内存访问模式，主要区别在于是否按照内存系统的时序产生请求和响应。

Atomic访问通过一个调用直接得到访问结果，同时返回一个表示访问延迟的Tick。它可以反映某些访问延迟，但不会像Timing访问那样将请求拆成发送和响应两个异步阶段。AtomicSimpleCPU主要使用这种方式。

Timing访问通过`sendTimingReq()`发送请求。如果下游组件暂时不能接受请求，发送方需要等待并处理重试；如果请求被接受，后续还需要等待`recvTimingResp()`接收响应。TimingSimpleCPU、MinorCPU和O3CPU使用Timing方式与内存系统交互。

Functional访问主要用于调试、初始化和检查点恢复等场景，它强调立即访问当前系统状态，而不是模拟一次真实的时序传输。比如Workload在初始化时把ELF程序段写入内存，就可以通过物理内存代理完成这种直接写入。

三种模式的关系可以简单概括为：

| 访问模式 | 是否等待异步响应 | 是否体现内存层次时序 | 主要用途 |
| --- | --- | --- | --- |
| Atomic | 通常不需要 | 以返回延迟的方式体现 | 功能验证和快速仿真 |
| Timing | 需要 | 通过事件完整体现 | 时序和内存系统研究 |
| Functional | 不模拟正常请求时序 | 不关注访问延迟 | 初始化、调试和状态访问 |

CPU模型的内存访问模式还必须和System的`mem_mode`匹配。AtomicSimpleCPU要求系统处于`atomic`模式，TimingSimpleCPU、MinorCPU和O3CPU则要求系统处于`timing`模式。CPU的`memory_mode()`类方法就是用来声明这一要求的。

**Full System、Syscall Emulation与Workload**

Gem5常见的运行方式可以分为Full System和Syscall Emulation两类。Full System模式模拟的是一个相对完整的目标机系统，目标机程序会直接访问模拟出来的内存和设备，必要时还会运行目标机操作系统。我们前面运行裸机程序和启动Linux，都属于这一类。

Syscall Emulation模式不完整模拟目标机操作系统，而是由Gem5截获目标程序发出的系统调用，再使用宿主机环境或者Gem5内部逻辑完成对应操作。这种方式启动速度快，适合运行单个用户态程序，但它并不适合验证完整的启动流程、设备驱动和操作系统内核行为。

`Workload`描述的是整个系统的软件运行环境。在RISC-V裸机配置中，我们使用：

```python
system.workload = RiscvBareMetal()
system.workload.bootloader = "hello32"
```

`RiscvBareMetal`会读取ELF文件，提取其中的代码段、数据段、符号表和入口地址，并把程序镜像写入模拟内存。初始化线程时，它会调用RISC-V的Reset逻辑，将PC设置到ELF入口地址。

而`Process`主要服务于SE模式。它描述一个用户态进程的地址空间、程序参数、环境变量、文件描述符和系统调用状态。下面这种配置就是典型的SE模式：

```python
process = Process()
process.cmd = [binary]

system.cpu.workload = process
system.workload = SEWorkload.init_compatible(binary)
```

因此，在Full System裸机配置中，重点是`system.workload`和`RiscvBareMetal`，暂时不需要实现Process支持。只有当我们希望让CPU运行Linux用户程序，并通过Gem5模拟系统调用时，才需要深入处理Process和SEWorkload。

## 3.2 TimingSimpleCPU中一段程序的执行路径

前面分别介绍了事件、CPU、端口和内存请求。下面用一段很小的RISC-V程序，把这些内容串成一次完整的`TimingSimpleCPU`执行过程。为了突出事件和请求的关系，假设程序被加载到`0x80000000`，并且：

```asm
0x80000000: ADDI x1, x0, 5
0x80000004: ADDI x2, x0, 7
0x80000008: ADD  x3, x1, x2
0x8000000c: LW   x4, 0(x5)
0x80000010: ADD  x6, x3, x4
```

同时假设：

```text
x5 = 0x80001000
内存[0x80001000] = 10
初始PC = 0x80000000
```

程序执行后，寄存器结果应当为：

```text
x1 = 5
x2 = 7
x3 = 12
x4 = 10
x6 = 22
```

这里的代码是根据Gem5实际处理过程整理出的简化伪代码，函数名称和调用关系与源码保持对应，但省略了统计、调试、Drain和错误处理等细节。

### 3.2.1 CPU执行事件的定义与触发

`TimingSimpleCPU`通常使用`fetchEvent`作为取指阶段的驱动事件。它在CPU对象中保存一个回调函数，回调函数负责调用CPU的`fetch()`：

```cpp
class TimingSimpleCPU : public BaseTimingSimpleCPU
{
  private:
    EventFunctionWrapper fetchEvent;

  public:
    void fetch();
};

TimingSimpleCPU::TimingSimpleCPU(const Params &params)
    : BaseTimingSimpleCPU(params),
      fetchEvent(
          [this] { this->fetch(); },
          "TimingSimpleCPU fetch")
{
}
```

构造函数这里只是建立了这样的关系：

```text
fetchEvent发生
    |
    v
调用TimingSimpleCPU::fetch()
```

它并不会在构造CPU时立即执行`fetch()`。CPU完成初始化、程序加载和线程激活后，才会将`fetchEvent`安排到事件队列中：

```cpp
fetchEvent.schedule(clockEdge());
```

当`m5.simulate()`开始运行时，Gem5的事件循环会不断从事件队列中取出最早的事件。简化后的事件循环如下：

```cpp
while (eventQueue.hasNextEvent()) {
    Event *event = eventQueue.nextEvent();
    curTick = event->when();
    event->process();
}
```

`fetchEvent`的`process()`最终执行它保存的回调函数，因此第一次调用链可以表示为：

```text
m5.simulate()
    |
    v
Gem5事件循环
    |
    v
取出fetchEvent
    |
    v
fetchEvent.process()
    |
    v
调用TimingSimpleCPU::fetch()
```

### 3.2.2 第一次取指：ADDI x1, x0, 5

第一次调用`fetch()`时，CPU的PC是`0x80000000`。CPU根据PC创建一个指令读取请求：

```cpp
void TimingSimpleCPU::fetch()
{
    Addr pc = thread->pcState().instAddr();

    RequestPtr req = makeFetchRequest(
        pc, sizeof(MachInst), Request::INST_FETCH);

    PacketPtr pkt = new Packet(req, MemCmd::ReadReq);

    if (!icachePort.sendTimingReq(pkt)) {
        status = IcacheRetry;
        return;
    }

    status = IcacheWaitResponse;
}
```

这段代码表达的不是一次普通的函数读取，而是向指令Cache发送一个Timing请求：

```text
TimingSimpleCPU
    |
    | 读取0x80000000处的4字节
    v
指令Cache
    |
    v
总线和内存系统
```

如果Cache暂时不能接受请求，`sendTimingReq()`返回失败，CPU保存请求并等待`recvReqRetry()`通知后重试。如果请求被接受，CPU进入`IcacheWaitResponse`状态，当前`fetch()`结束。此时第一条指令还没有执行，因为机器码还没有返回。

假设Cache未命中，内存系统需要若干个Tick才能返回数据。之后，响应Packet沿原路径返回CPU，指令端口调用类似下面的处理函数：

```cpp
void TimingSimpleCPU::recvTimingResp(PacketPtr pkt)
{
    if (pkt == ifetch_pkt)
        completeIfetch(pkt);
    else
        completeDataAccess(pkt);
}
```

`completeIfetch()`收到机器码后，才开始解码和执行。对于普通算术指令，取指响应处理函数可以直接执行指令；对于`LW`或`SW`等访存指令，则需要启动数据访问，等待数据请求完成：

```cpp
void TimingSimpleCPU::completeIfetch(PacketPtr pkt)
{
    MachInst mach_inst = pkt->get< MachInst >();

    curStaticInst = decoder.decode(mach_inst);

    Fault fault = NoFault;

    if (curStaticInst->isMemRef()) {
        fault = curStaticInst->initiateAcc(
            &thread_info, traceData);

        if (data_request_pending)
            return;
    } else {
        fault = curStaticInst->execute(
            &thread_info, traceData);
    }

    postExecute();
    advancePC(fault);

    fetchEvent.schedule(clockEdge(Cycles(1)));
}
```

对于本例，Decoder将机器码识别为：

```asm
ADDI x1, x0, 5
```

指令执行逻辑完成：

```text
读取x0 = 0
计算0 + 5 = 5
写回x1 = 5
PC更新为0x80000004
```

随后，CPU重新安排`fetchEvent`，准备取下一条指令。也就是说，TimingSimpleCPU执行普通算术指令时，过程不是：

```text
fetch()直接执行ADD
```

而是：

```text
fetchEvent触发fetch()
    |
    v
发送取指请求
    |
    v
等待指令响应
    |
    v
completeIfetch()
    |
    v
解码并执行指令
    |
    v
安排下一次fetchEvent
```

### 3.2.3 后续算术指令的执行

下一次`fetchEvent`触发时，PC已经变为`0x80000004`。CPU重复同样的流程，取出并执行：

```asm
ADDI x2, x0, 7
```

执行结果为：

```text
x2 = 7
PC = 0x80000008
```

再下一次取指得到：

```asm
ADD x3, x1, x2
```

此时前两条指令已经完成，因此CPU可以读取到：

```text
x1 = 5
x2 = 7
```

执行`ADD`后：

```text
x3 = 12
PC = 0x8000000c
```

对于这三条算术指令，每条指令都遵循下面的循环：

```text
根据PC发起取指请求
    |
等待指令Cache或内存响应
    |
Decoder生成StaticInst
    |
StaticInst读取寄存器并执行
    |
更新寄存器和PC
    |
安排下一次fetchEvent
```

`TimingSimpleCPU`是顺序执行模型，因此后一条指令不会在前一条指令写回之前执行。它虽然模拟了请求和响应的时间，但没有像O3CPU那样同时维护大量乱序执行的指令。

### 3.2.4 Load指令的执行

当PC为`0x8000000c`时，CPU取出：

```asm
LW x4, 0(x5)
```

取指响应返回后，Decoder完成解码，CPU根据寄存器计算有效地址：

```text
有效地址 = x5 + 0
        = 0x80001000
```

由于这是Load指令，CPU不能像`ADD`那样立即完成写回，而是通过数据端口发起新的Timing请求：

```cpp
Fault TimingSimpleCPU::executeMemoryInstruction()
{
    Addr addr = readIntReg(rs1) + immediate;

    RequestPtr req = makeDataRequest(
        addr, 4, Request::READ);

    PacketPtr pkt = new Packet(req, MemCmd::ReadReq);

    if (!dcachePort.sendTimingReq(pkt)) {
        status = DcacheRetry;
        return NoFault;
    }

    data_pkt = pkt;
    status = DcacheWaitResponse;
    return NoFault;
}
```

这段代码表示：

```text
取指完成
    |
    v
计算0x80001000
    |
    v
通过数据端口发送Load请求
    |
    v
CPU进入DcacheWaitResponse状态
```

此时CPU不会把未知的数据写入`x4`，也不会直接执行下一条指令，而是保存当前Load指令，等待数据响应。若数据Cache未命中，请求还会继续经过总线和内存控制器。

当内存返回：

```text
内存[0x80001000] = 10
```

CPU收到数据响应后调用数据访问完成函数：

```cpp
void TimingSimpleCPU::completeDataAccess(PacketPtr pkt)
{
    Fault fault = curStaticInst->completeAcc(
        pkt, &thread_info, traceData);

    postExecute();
    advancePC(fault);

    fetchEvent.schedule(clockEdge(Cycles(1)));
}
```

`completeAcc()`完成Load指令的最后部分：

```text
从Packet中读取10
写回x4 = 10
PC更新为0x80000010
安排下一次fetchEvent
```

因此，`LW`比`ADD`多出了一段数据访问等待过程：

```text
取指
    |
    v
解码LW
    |
    v
计算有效地址
    |
    v
发送数据请求
    |
    v
等待数据响应
    |
    v
完成Load并写回寄存器
    |
    v
更新PC
```

### 3.2.5 这一过程中的事件分工

对于上述程序，事件和函数的职责可以总结为：

| 对象或函数 | 作用 |
| --- | --- |
| `fetchEvent` | 在指定仿真时间触发CPU取指 |
| `fetch()` | 根据PC创建并发送取指请求 |
| 指令Cache事件 | 查找指令、处理命中或向下级发送请求 |
| `recvTimingResp()` | 接收Cache或内存返回的Packet |
| `completeIfetch()` | 保存机器码、解码并执行非访存指令 |
| `dcachePort` | 发送Load或Store数据请求 |
| `completeDataAccess()` | 完成Load或Store的访存阶段 |
| `advancePC()` | 根据指令结果更新PC |
| `EventQueue` | 按仿真时间顺序调用上述事件和回调 |

整个程序的执行不是由一个函数从头运行到尾，而是由多个事件交替推进：

```text
CPU.fetchEvent触发
    |
    v
CPU发送取指请求
    |
    v
Cache或内存响应事件触发
    |
    v
CPU完成解码和执行
    |
    v
CPU安排下一次fetchEvent
    |
    v
重复上述过程
```

如果把仿真时间用`T0`、`T1`和`T2`表示，而不指定具体Tick数，那么这段程序的主要事件顺序可以写成：

```text
T0：fetchEvent触发，发送0x80000000取指请求
T1：收到响应，执行ADDI x1,x0,5，PC变为0x80000004
T2：收到响应，执行ADDI x2,x0,7，PC变为0x80000008
T3：收到响应，执行ADD x3,x1,x2，PC变为0x8000000c
T4：收到响应，解码LW并发送0x80001000数据请求
T5：收到数据10，写回x4，PC变为0x80000010
T6：收到响应，执行ADD x6,x3,x4
```

这里的`T0`到`T6`并不一定间隔相同。Cache命中、Cache未命中、总线拥塞、内存控制器排队和请求重试都会影响实际时间。这正是`TimingSimpleCPU`与`AtomicSimpleCPU`的区别：前者通过事件和响应体现这些时序过程，后者通常在一次Atomic访问中直接获得访问结果。

## 3.3 Gem5微架构模型

**ISA与微架构**

ISA和微架构是处理器设计中的两个不同概念。ISA规定软件能够看到的处理器行为，例如有哪些指令、寄存器如何组织、异常如何进入、内存访问遵循什么规则；微架构则规定这些指令在硬件内部如何被取出、保存、调度和执行。

例如，`ADD x3, x1, x2`在ISA层面的含义是将两个寄存器相加，并把结果写入另一个寄存器。至于这个加法是在一条简单执行路径中完成，还是经过多级流水线，或者被乱序执行单元调度，并不是ISA规定的内容，而是微架构模型决定的。

Gem5利用这种分层关系，使多个CPU模型能够复用同一套RISC-V指令实现。AtomicSimpleCPU可以执行RISC-V指令，TimingSimpleCPU、MinorCPU和O3CPU同样可以执行这些指令，但它们对指令执行时间和指令之间关系的描述不同。

**CPU模型的继承关系**

Gem5的CPU模型大体从`BaseCPU`开始向下派生。`BaseCPU`提供CPU对象的通用能力，例如时钟、线程上下文、CPU编号、Workload、ISA、MMU、中断控制器和指令、数据端口等。

`BaseSimpleCPU`在此基础上增加了简单CPU共用的执行环境，包括当前线程、当前静态指令、线程信息、取指请求、指令预处理、指令后处理和PC更新等接口。AtomicSimpleCPU和TimingSimpleCPU都建立在这一层之上。

更具体地说，RISC-V相关的Python类通过多重继承将微架构模型和ISA模型组合起来：

```python
class RiscvAtomicSimpleCPU(BaseAtomicSimpleCPU, RiscvCPU):
    mmu = RiscvMMU()

class RiscvTimingSimpleCPU(BaseTimingSimpleCPU, RiscvCPU):
    mmu = RiscvMMU()

class RiscvMinorCPU(BaseMinorCPU, RiscvCPU):
    mmu = RiscvMMU()

class RiscvO3CPU(BaseO3CPU, RiscvCPU):
    mmu = RiscvMMU()
```

这里的`RiscvCPU`更像一个ISA适配层，它提供RISC-V所需的Decoder、MMU、ISA和中断控制器类型；`BaseAtomicSimpleCPU`、`BaseTimingSimpleCPU`、`BaseMinorCPU`和`BaseO3CPU`则分别提供不同的微架构执行方式。

**AtomicSimpleCPU**

AtomicSimpleCPU是Gem5中最简单的CPU模型之一。它不会详细模拟流水线，也不会让多条指令同时处于不同的执行阶段，而是按照顺序取得一条指令并完成执行。它通常使用Atomic方式访问内存，因此执行速度较快，适合验证程序功能、测试设备连接和调试ISA实现。

其主要执行循环位于`src/cpu/simple/atomic.cc`的`AtomicSimpleCPU::tick()`中。简化之后，代码结构如下：

```cpp
Fault fault = NoFault;

setupFetchRequest(ifetch_req);
fault = thread->mmu->translateAtomic(
    ifetch_req, thread->getTC(), BaseMMU::Execute);

if (fault == NoFault) {
    fetchInstMem();
    preExecute();

    if (curStaticInst)
        fault = curStaticInst->execute(&t_info, traceData);

    postExecute();
}

advancePC(fault);
```

实际代码还包含中断检查、PC事件、微操作、统计、Drain和停顿处理，但基本执行顺序就是取指、解码、执行和更新PC。

需要注意，AtomicSimpleCPU并不是完全没有延迟。它可以通过Atomic访问得到内存系统返回的延迟，也可以根据配置统计指令Cache和数据Cache的停顿。但是这种延迟不会完整地改变CPU和内存之间的异步交互过程，因此它不能代替真正的Timing模型进行详细的时序研究。

**TimingSimpleCPU**

TimingSimpleCPU仍然是一种顺序执行的简单CPU，但它采用Timing请求访问内存。一次取指不能简单地在函数调用中完成，而要经历发起请求、等待响应、接收数据和恢复执行几个阶段。

CPU发起请求时调用类似下面的接口：

```cpp
icachePort.sendTimingReq(ifetch_pkt)
```

如果下游组件接受请求，CPU等待之后的响应；如果请求被拒绝，CPU进入重试状态，等收到`recvReqRetry()`后再次发送。指令数据返回时，指令端口的`recvTimingResp()`被调用，CPU再恢复译码和执行。

TimingSimpleCPU因此能够体现Cache未命中、总线阻塞、内存控制器排队以及不同设备访问延迟。它仍然不会像MinorCPU或O3CPU那样同时维护大量在途指令，但已经能够用于研究CPU与内存系统之间的时序关系。

**MinorCPU和O3CPU**

MinorCPU是一个顺序流水线模型，内部明确划分了取指、译码、执行和提交等阶段。指令可以在流水线中重叠运行，但整体上仍然保持顺序执行和顺序提交。它比TimingSimpleCPU更接近一个实际的流水线处理器，同时保留了较为清晰的结构，适合研究流水线停顿、分支和功能单元。

O3CPU则用于模拟乱序执行处理器。它会在取指之后将指令放入指令队列，经过寄存器重命名、发射、执行、写回和提交等阶段。不同指令可能按照操作数准备情况乱序执行，但最终仍然按照程序顺序提交，从而保证精确异常和软件可见状态的正确性。

O3CPU中常见的结构包括取指单元、译码单元、重命名逻辑、发射队列、功能单元、Load/Store Queue、物理寄存器文件和提交逻辑。这些结构使它能够模拟较高的指令级并行度，但也使模型复杂度和仿真开销明显增加。

MinorCPU和O3CPU都使用Timing方式访问内存。MinorCPU通常需要等待流水线中对应的访存指令完成，O3CPU则可以同时维护多个未完成的内存请求，并根据依赖关系和提交顺序处理返回结果。

**不同CPU模型的选择**

四种CPU模型并不是简单地从“功能少”到“功能多”排列，而是对应不同的研究目标。AtomicSimpleCPU更加重视功能正确性和仿真速度；TimingSimpleCPU在简单顺序执行的基础上加入了内存时序；MinorCPU强调流水线结构；O3CPU则强调乱序执行和指令级并行。

| CPU模型 | 执行方式 | 内存访问 | 主要特点 |
| --- | --- | --- | --- |
| AtomicSimpleCPU | 顺序执行 | Atomic | 结构简单，仿真速度快 |
| TimingSimpleCPU | 顺序执行 | Timing | 能够体现内存访问时序 |
| MinorCPU | 顺序流水线 | Timing | 具有明确的流水线阶段 |
| O3CPU | 乱序执行、顺序提交 | Timing | 能够模拟较高指令级并行 |

如果目标是验证RV32I指令语义和外围连接是否正确，通常应先采用简单的执行组织，而不是立即建立复杂的缓存层次或乱序流水线。因此，可以先参考AtomicSimpleCPU的执行方式，让一条指令在一次CPU事件中完成；后续如果需要研究内存延迟，再把访存部分改造成Timing接口。

不过，直接继承AtomicSimpleCPU也存在一个重要限制。AtomicSimpleCPU中的`tick()`是其内部执行事件，并不是一个适合通过继承直接重写的虚函数。也就是说，如果只是让新的CPU类继承AtomicSimpleCPU，再在子类中定义一个同名函数，并不能自动替换父类已经绑定到`tickEvent`中的执行逻辑。要实现真正独立的CPU执行循环，应当从`BaseSimpleCPU`重新组织事件和端口，或者复制AtomicSimpleCPU中需要复用的基础代码后进行改造。

## 3.4 ISA与架构支持

**ISA负责规定什么是正确的执行**

指令集架构是软件和处理器之间的接口。对于RISC-V来说，ISA不仅包括加法、减法、加载、存储和跳转等指令，还包括寄存器组织、立即数编码、程序计数器变化、内存访问规则、异常中断、特权级和控制状态寄存器等内容。

因此，ISA不能简单理解为一张指令编码表。一个CPU即使能够识别某条机器码，如果没有按照ISA规定更新PC、处理寄存器、检查地址对齐或者产生异常，那么它仍然不是一个行为正确的RISC-V处理器。

**Gem5中的RISC-V适配层**

Gem5通过`RiscvCPU`将RISC-V架构的几个核心组件提供给不同CPU模型：

```python
class RiscvCPU:
    ArchDecoder = RiscvDecoder
    ArchMMU = RiscvMMU
    ArchInterrupts = RiscvInterrupts
    ArchISA = RiscvISA
```

CPU模型只需要继承合适的基础类和`RiscvCPU`，就可以使用RISC-V的Decoder、MMU、ISA和中断控制器。具体的组合方式由Python配置类完成，C++ CPU模型则通过通用接口访问这些架构对象。

这种设计意味着，`RiscvTimingSimpleCPU`和`RiscvO3CPU`可以使用同一套RISC-V指令描述，但它们的取指、调度和内存等待方式完全不同。指令的语义属于ISA，指令何时进入执行阶段、是否能够和其他指令重叠，则属于微架构。

**寄存器与ThreadContext**

RISC-V的整数寄存器为`x0`到`x31`。其中`x0`始终读取为零，任何写入都不会改变它的值。RV32和RV64的主要区别之一，是整数寄存器和相关操作的数据宽度不同。

在Gem5中，寄存器并不是简单地存放在CPU类的一个数组中。CPU通过`ThreadContext`或执行上下文访问体系结构状态。执行一条指令时，StaticInst可以通过执行上下文读取源寄存器，并将结果写回目标寄存器。这样，AtomicSimpleCPU、TimingSimpleCPU、MinorCPU和O3CPU都可以使用同一套指令语义，而不需要让每个CPU模型分别重新实现所有RISC-V指令。

在实际硬件中，寄存器文件属于CPU内部结构；在Gem5中，寄存器状态通常由线程上下文和ISA对象共同管理。CPU模型负责在正确的时机调用读写接口，ISA实现则负责解释这些寄存器在体系结构上的含义。

**PCState和控制流指令**

程序计数器决定下一条要执行的指令地址。RISC-V普通指令通常为32位，启用压缩扩展后还可能出现16位指令。因此，Gem5没有只使用一个简单的整数变量表示PC，而是通过RISC-V的PCState保存当前指令地址、下一条地址、指令长度以及分支状态等信息。

对于普通算术指令，执行结束后PC通常顺序增加；对于条件分支，是否跳转由比较结果决定；对于`JAL`和`JALR`，PC会被修改为目标地址，同时还需要把返回地址写入目标寄存器；对于异常，PC则由异常处理逻辑设置为trap vector。CPU的通用执行框架只负责调用PC更新接口，具体的PC状态变化由ISA实现提供。

**Decoder、StaticInst和指令执行**

CPU从内存中取得机器码后，需要将它转换成可以执行的指令对象。RISC-V Decoder根据opcode、funct3、funct7以及其他字段判断指令类型，并生成对应的StaticInst对象。

`StaticInst`是Gem5中对静态指令的抽象。它保存一条指令的操作类型、源寄存器和目标寄存器数量、是否为访存指令、是否为控制流指令等信息，并提供执行相关接口。RISC-V指令通常在此基础上派生出具体的算术指令、分支指令、访存指令和原子指令。

一条普通算术指令的执行过程大致为：

```text
读取机器码
    |
Decoder解析指令字段
    |
生成RISC-V StaticInst
    |
读取源寄存器
    |
完成算术或逻辑运算
    |
写回目标寄存器
    |
更新PC
```

对于Load和Store指令，执行过程还会调用`initiateAcc()`和`completeAcc()`等内存访问接口。不同微架构模型可以在不同时间调用这些接口，但指令最终表现出的体系结构结果必须保持一致。

RISC-V的指令描述主要位于`src/arch/riscv/isa`相关目录，包括指令格式、位域、操作数和解码规则等内容。Gem5会根据这些描述生成相应的C++代码。这样做可以减少手工编写大量解码代码的工作，并让指令定义与执行语义保持相对集中。

**MMU、TLB和内存访问**

CPU执行一条访存指令时，首先要根据基址寄存器和立即数计算有效地址。之后，地址需要经过MMU处理。MMU可能需要查询TLB，必要时还要进行页表遍历，并检查访问权限、地址对齐和物理内存属性。

在当前的裸机RV32I实验中，程序通常直接运行在物理地址空间或简单的恒等映射环境中，不需要立即实现完整的分页系统。但这并不意味着可以完全忽略MMU，因为取指和数据访问仍然需要经过地址翻译接口，并且需要处理基本的访问错误和地址对齐问题。

对于UART这类内存映射设备，CPU发出的访问不会到达普通RAM，而是通过总线根据地址范围转发到UART设备。设备收到写请求后，可能将数据输出到终端；收到读请求时，则返回设备当前状态。因此，CPU看到的是普通的Load/Store指令，系统的其他部分则根据地址将其解释为设备访问。

**Fault、异常和中断**

Gem5中的`Fault`表示一条指令执行过程中产生的异常、陷阱或中断。RISC-V中常见的Fault包括非法指令、指令访问错误、Load或Store地址未对齐、Load或Store访问错误、`ecall`、`ebreak`以及各种外部中断。

一条指令执行后，通常会返回一个`Fault`对象：

```cpp
Fault fault = curStaticInst->execute(&t_info, traceData);
```

如果执行正常，返回值为`NoFault`；如果出现异常，则返回具体的Fault。CPU随后调用Fault的处理接口。Full System模式下，RISC-V Fault处理逻辑会根据当前特权级和异常委托设置，更新`mcause`、`mepc`、`mtval`和`mstatus`等CSR，并将PC跳转到`mtvec`指定的异常入口。

异常处理过程可以表示为：

```text
指令产生异常
    |
保存发生异常的PC
    |
记录异常原因和附加信息
    |
修改特权级和状态寄存器
    |
PC跳转到trap vector
    |
执行软件异常处理程序
```

在SE模式下，由于没有完整的目标机异常处理环境，某些Fault会直接交给Gem5处理，严重情况下会终止仿真。对于当前的裸机CPU，初期至少需要正确处理非法指令、地址未对齐和访问错误；当需要运行更复杂的裸机程序时，再逐步加入`ecall`、`ebreak`、CSR、`mret`和中断机制。

**ISA与微架构的解耦**

Gem5中一条指令的执行可以被拆成两个层次。ISA层负责解释这条指令是什么、读取哪些寄存器、产生什么结果、是否访问内存以及发生异常时应该产生什么Fault；微架构层负责决定什么时候取指、什么时候执行、内存访问是否阻塞、流水线如何推进以及指令何时提交。

例如，`LW x5, 0(x6)`在ISA层面规定了地址计算、内存读取、符号扩展和寄存器写回的语义。AtomicSimpleCPU可以在一个执行循环中完成这些操作，TimingSimpleCPU可能需要等待数据响应，MinorCPU需要把它放入流水线，O3CPU则可能让它和其他指令乱序执行。但最终写入`x5`的值必须相同。

这种解耦设计对自定义CPU很重要。我们可以复用Gem5现有的RISC-V Decoder、StaticInst、MMU和Fault支持，只重新实现自己的CPU执行组织方式。也可以在教学或研究目的下，仅实现一个简化的RV32I解码和执行模块，同时继续复用Gem5的Workload、内存系统和设备模型。

**RV32I CPU的实现范围**

对于第一版RV32I CPU，不需要一开始就实现完整的RISC-V特权架构和所有扩展。比较合理的实现顺序是先完成整数寄存器和RV32I基础指令，包括`LUI`、`AUIPC`、算术逻辑立即数指令、寄存器算术逻辑指令、Load、Store、条件分支、`JAL`和`JALR`。

在能够运行简单计算程序之后，再加入`FENCE`、`ECALL`、`EBREAK`和基本异常处理。对于裸机Hello World，还需要保证普通内存访问和UART内存映射访问能够正常工作。RV32M乘除法、RV32A原子操作、RV32C压缩指令、分页和Linux启动支持，则可以放到后续阶段。

需要特别注意，编译器生成的程序不一定只使用RV32I。测试程序可能使用了`rv32ima`等扩展。如果希望严格验证RV32I实现，应当使用`-march=rv32i`重新编译测试程序，并检查生成的指令是否超出CPU支持范围。

## 3.5 Lab3：自定义CPU外围框架

**Lab3的目标**

前面四节介绍的是Gem5的基本运行机制，接下来回到实际代码。lab3的目标不是立即完成一个功能完整的CPU，而是先把自定义CPU接入Gem5所需要的外围框架打通。具体来说，需要完成SimObject注册、C++类定义、构建系统接入、系统配置、RISC-V ISA绑定、Workload加载和裸机程序运行。

当前lab3能够运行Hello World，但这个`SingleCPU`还没有独立的取指和执行逻辑。它本质上是一个继承了AtomicSimpleCPU的自定义名称和C++包装类，实际指令执行仍然由父类完成。这一步的意义在于先验证CPU对象和Gem5外围系统之间的接口是正确的，后续可以在不改变内存、UART和Workload配置的情况下替换CPU内部实现。

**SingleCPU.py**

当前Python定义如下：

```python
from m5.params import *
from m5.objects.BaseAtomicSimpleCPU import BaseAtomicSimpleCPU
from m5.objects.RiscvCPU import RiscvCPU
from m5.objects.RiscvMMU import RiscvMMU

class SingleCPU(BaseAtomicSimpleCPU, RiscvCPU):
    type = "SingleCPU"
    cxx_class = "gem5::SingleCPU"
    cxx_header = "labs/lab3/SingleCPU.hh"

    mmu = RiscvMMU()
```

`BaseAtomicSimpleCPU`表示这个CPU采用AtomicSimpleCPU的基础参数和内存模式。它的`memory_mode()`返回`atomic`，因此系统配置中需要使用：

```python
system.mem_mode = "atomic"
```

`RiscvCPU`则把RISC-V相关的架构组件绑定到这个CPU上。`mmu = RiscvMMU()`显式指定使用RISC-V的MMU实现。由于当前CPU仍然继承父类执行逻辑，所以它可以直接使用Gem5已有的RISC-V Decoder、寄存器、PCState和指令实现。

注意这里继承了`RiscvCPU`，实际上继承的是RISCV架构组件类型，而继承`BaseAtomicSimpleCPU`则是继承了CPU执行模型，即上文提到的微架构和ISA独立。必须显式指定`mmu = RiscvMMU()`，这样才成功创建了一个MMU实例，即把`BaseAtomicSimpleCPU`中的这个`mmu`执行模型绑定给了`RiscvMMU`。

**SingleCPU.hh和SingleCPU.cc**

C++头文件声明了真正的Gem5 CPU对象：

```cpp
class SingleCPU : public AtomicSimpleCPU
{
  public:
    PARAMS(SingleCPU);

    explicit SingleCPU(const Params &params);
};
```

这里的继承关系必须和Python侧的CPU模型保持一致。Python侧继承`BaseAtomicSimpleCPU`，对应的C++基类就是`AtomicSimpleCPU`。`PARAMS(SingleCPU)`会引入由Gem5生成的`SingleCPUParams`，构造函数通过这个参数对象接收Python配置中的参数。

源文件中的构造函数目前只调用父类构造函数：

```cpp
SingleCPU::SingleCPU(const Params &params)
    : AtomicSimpleCPU(params)
{
}
```

这意味着`SingleCPU`目前只完成了类型包装，没有增加新的执行行为。Gem5创建`SingleCPU`对象后，父类会初始化请求对象、指令端口、数据端口、线程信息和CPU事件，并继续使用`AtomicSimpleCPU::tick()`完成指令执行。

**SConscript和构建**

lab3中的`SConscript`通过两条语句把对象加入构建系统：

```python
SimObject("SingleCPU.py", sim_objects=["SingleCPU"])
Source("SingleCPU.cc")
```

前者负责处理Python SimObject定义，并生成参数头文件；后者负责编译C++实现。使用`EXTRAS="$PWD/labs"`后，Gem5会进入`labs`目录寻找其中的`SConscript`，从而发现lab3中的自定义CPU。

完成构建后，`SingleCPU`不需要在配置脚本中手工导入Python文件。因为它已经被编译系统注册并加入生成的`m5.objects`模块，可以直接通过：

```python
from m5.objects import *

system.cpu = SingleCPU()
```

创建对象。手工再次导入并注册同一个SimObject，反而可能导致重复注册错误。

**riscv_single.py系统配置**

lab3的系统配置沿用了前面裸机实验的基本结构。首先创建系统、时钟域和内存范围：

```python
system = System()
system.clk_domain = SrcClockDomain()
system.clk_domain.clock = "1GHz"
system.clk_domain.voltage_domain = VoltageDomain()

system.mem_mode = "atomic"
system.mem_ranges = [AddrRange(start=0x80000000, size="128MB")]
```

随后创建自定义CPU并设置RISC-V架构：

```python
system.cpu = SingleCPU()
system.cpu.isa = [RiscvISA(riscv_type="RV32", enable_rvv=False)]
```

这里的`RV32`表示使用32位RISC-V状态和寄存器宽度。`enable_rvv=False`关闭向量扩展，但它并不自动把所有其他扩展删除。严格的RV32I测试还需要从软件编译选项上控制指令扩展，不能只依赖这个参数。

CPU的指令端口和数据端口连接到总线，内存控制器连接到总线的另一侧：

```python
system.membus = SystemXBar()
system.cpu.icache_port = system.membus.cpu_side_ports
system.cpu.dcache_port = system.membus.cpu_side_ports

system.mem_ctrl = MemCtrl()
system.mem_ctrl.dram = DDR3_1600_8x8()
system.mem_ctrl.dram.range = system.mem_ranges[0]
system.mem_ctrl.port = system.membus.mem_side_ports
```

虽然当前配置中CPU直接连接到总线，没有显式创建Cache，但CPU端口仍然保留了指令和数据访问的区分。后续加入Cache或自定义内存层次时，可以在这些端口之间插入新的组件。

HiFive平台负责提供RISC-V板级设备，包括UART、PLIC和片上IO等。UART采用内存映射方式连接到系统总线，程序向固定地址写入字符后，访问请求会被总线转发到UART设备，最终显示在Gem5的终端输出中。

**RiscvBareMetal与程序启动**

系统配置最后指定裸机Workload：

```python
system.workload = RiscvBareMetal()
system.workload.bootloader = "hello32"
```

`RiscvBareMetal`在初始化时调用ELF加载器读取程序文件，获得程序的入口地址和符号表。随后通过物理内存代理把ELF中的各个段写入系统内存，并通过RISC-V Reset逻辑设置CPU初始状态。

因此，lab3启动裸机程序的过程可以概括为：

```text
读取hello32 ELF文件
        |
将.text、.data等段写入模拟内存
        |
获得ELF入口地址
        |
设置RISC-V初始特权级和PC
        |
激活CPU线程
        |
调度CPU执行事件
```

CPU创建线程上下文后，`m5.instantiate()`完成所有C++对象初始化，`m5.simulate()`开始处理事件。此时，`SingleCPU`虽然是自定义类型，但它仍然调用父类的Atomic执行循环。父类从PC对应的地址取出指令，经RISC-V Decoder解码后执行；当程序向UART地址写入字符时，请求经过总线到达平台设备，最后输出`Hello, World!`。

**当前实现与真正单周期CPU的区别**

当前lab3已经完成了自定义CPU外围框架，但还没有完成真正的单周期CPU。两者之间的区别需要明确：

第一，当前`SingleCPU`没有自己的寄存器堆和指令执行单元，寄存器和指令语义仍然由Gem5已有的RISC-V ISA实现提供。

第二，当前`SingleCPU`没有自己的取指和执行状态机，事件仍然由AtomicSimpleCPU父类管理，执行流程仍然是父类定义的流程。

第三，当前模型虽然可以按照简单顺序方式执行指令，但它并不代表已经实现了硬件意义上的单周期数据通路。真正的单周期CPU需要明确设计PC、指令存储器、寄存器堆、立即数生成器、ALU、数据存储器、控制器和写回路径，并规定一条指令在一个模拟周期内完成哪些操作。

因此，lab3当前更准确的定位是“自定义CPU的Gem5外围接入框架”。它已经打通了从SimObject注册、编译、系统连接、程序加载到仿真运行的链路，后续只需要逐步替换CPU内部执行逻辑，就可以继续使用现有的内存、UART、平台和Workload配置。

本章完成之后，我们已经能够从整体上理解Gem5是如何通过Python配置系统、C++ SimObject、事件队列、CPU微架构、ISA支持、内存系统和Workload共同完成一次仿真的，也明确了自定义CPU应该接入Gem5的哪些接口。下一步将在lab3的基础上分析`BaseSimpleCPU`的执行接口和线程状态，设计单周期CPU的内部结构，并逐步实现RV32I的取指、解码、执行、访存、异常和PC更新逻辑。
